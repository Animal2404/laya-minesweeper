# Laya Minesweeper

用 [Laya](https://github.com/NandhaKishorM/laya) 玩扫雷 —— 但架构上做了个刻意的设计:

> **代码负责数学, Laya 负责判断。**

![截图](shot.png)

---

## 先说结论(重要)

这个项目做了件可能和你预期相反的事。实测下来:

| | 表现 |
|---|---|
| 约束求解器 | 能精确算出每格的含雷概率, 自动通关 |
| **Laya** | **几乎恒定输出 ~51%, 没有判断力** |

界面上那张「Laya 的判断 vs 数学真值」对比表就是这个结论的证据。同一局里:

```
数学真值 21.0%  →  Laya 51.6%
数学真值 21.0%  →  Laya 50.6%
数学真值 21.0%  →  Laya 52.9%
```

十几个概率完全不同的格子, Laya 全给 ~51%。它**不区分**。

这不是接线错误 —— 是模型的适用范围问题。Laya 是文本蕴含模型(encoder + 分类头),
擅长「这段文本属于哪个类别」, 不擅长空间推理。同类现象我在贪吃蛇上也测到过:
问它「该往哪拐」每个 checkpoint 都答反, 换成问「鸟在缺口上面还是下面」才有干净的分级答案。

**所以本项目的价值不是"让 AI 玩扫雷", 而是把"它在哪不行"量化给你看。**
对比表存在的意义就是让你亲眼验证, 而不是听我说。

## 难度与棋盘

难度和棋盘尺寸**都可以自定义**。难度由两个因素决定：**总格数**和**雷密度**（雷数 ÷ 总格数）。
密度才是"难不难"的核心 —— 密度越高，逻辑可解的格子越少，必须猜的次数越多。

内置 7 档预设，每一项都标出总格数：

| 难度 | 棋盘 | **总格数** | 雷数 | 雷密度 | 说明 |
|---|---|---|---|---|---|
| 初级 | 9×9 | **81** | 10 | 12.3% | 等同经典 Windows 初级 |
| 简单 | 16×12 | **192** | 26 | 13.5% | |
| 中级 | 20×14 | **280** | 50 | 17.9% | |
| **经典·默认** | 30×16 | **480** | 99 | 20.6% | 等同经典 Windows 高级 |
| 困难 | 30×16 | **480** | 140 | 29.2% | 密度提高，猜测变多 |
| 专家 | 40×20 | **800** | 260 | 32.5% | |
| 地狱 | 50×24 | **1200** | 520 | 43.3% | 绝大多数局面靠猜 |

> 密度对照：经典 Windows 扫雷初级 12.3%、中级 15.6%、高级 20.6%。
> 超过 **35%** 之后，约束求解能确定的格子急剧减少，基本都是猜 —— 踩雷是常态而非 bug。

### 自定义

选「自定义 …」展开面板，直接填列 / 行 / 雷数：

- 实时校验并显示 **总格数（列×行）** 与密度评级
- 非法输入会被拦截（雷数 ≥ 总格数、列 < 5、行 < 5 等）
- 上限 80 列 × 60 行 = 4800 格

格子边长会**按容器实际宽度自动缩放**（10 ~ 26 px），大棋盘不会溢出；
窗口缩放时自动重算。

### 总格数显示在哪

需求要求"每个都要显示格子总数量"，所以三处都有：

1. **状态栏**第一项：`棋盘（总格数）` → `40×20 = 800`
2. **难度下拉每一项**：`专家 40×20=800 格 · 260 雷 · 32.5%`
3. **自定义面板实时提示**：`总格数 800（40×20）· 雷密度 25.0% · 极难，需大量猜测`

## 能不能通关「地狱」？——实测数据

先说结论：**不能，而且加强"推演深度"没有用。**

### 为什么深度不是杠杆

5 个固定中局 × 4 种深度，取平均：

| 深度 | 必然安全格 | 枚举格 | 合法方案 | 耗时 |
|---|---|---|---|---|
| 1 | 0.0 | 13.0 | 5.0 | 10.6 ms |
| **2** | **13.0** | 0.0 | 0.0 | 8.9 ms |
| 3 | 13.0 | 0.0 | 0.0 | 8.3 ms |
| 4 | 13.0 | 0.0 | 0.0 | 9.4 ms |

**深度 2 之后数字逐位相同** —— 约束在第 2 轮就收敛了，再迭代没有新信息。
所以界面默认是 2 步，3/4 是多余的。

### 真正的瓶颈是雷密度

50×24 = 1200 格，每档 40 局完整模拟（求解器能推就推，推不出就猜最低概率格）：

| 雷数 | 密度 | **通关率** | 平均猜测次数 | 平均推理次数 |
|---|---|---|---|---|
| 180 | 15.0% | **80%** | 1.9 | 9.4 |
| 240 | 20.0% | 30% | 3.8 | 13.8 |
| 300 | 25.0% | **0%** | 5.4 | 11.1 |
| 360 | 30.0% | 0% | 4.5 | 4.0 |
| 420 | 35.0% | 0% | 4.9 | 2.6 |
| 520 | 43.3% | 0% | 3.6 | 0.8 |

各预设难度的通关率：

| 难度 | 棋盘 | 密度 | 通关率 |
|---|---|---|---|
| 初级 | 9×9 | 12.3% | **90%** |
| 经典·默认 | 30×16 | 20.6% | **25%** |
| 困难 | 30×16 | 29.2% | 0% |
| 专家 | 40×20 | 32.5% | 0% |
| 地狱 | 50×24 | 43.3% | 0% |

**密度超过 25% 之后，通关率断崖式跌到 0。**

### 原因：猜测是"连续赌"

地狱难度平均只要猜 3.6 次，单次存活率 73% —— 看着还行。
但通关要求**每一次都猜对**：

```
0.73 ^ 3.6 ≈ 0.32     ← 单看这条还凑合
```

问题在于高密度下**可推理的格子太少**：平均只有 0.8 步是靠推理走的，
其余全靠猜，而且要连续猜对很多轮才能扫完 1200 格。
实测 40 局，一局都没过。

这不是代码缺陷 —— **扫雷本身就是 NP 完全问题**，高密度下不存在
能保证通关的多项式算法。任何求解器都会遇到同样天花板。

### Laya 在其中的作用

**没有作用。** 对比表里它的输出恒在 50~53%：

```
数学真值 50.0%  →  Laya 52.6%
数学真值 50.0%  →  Laya 50.6%
数学真值 50.0%  →  Laya 51.1%
```

它不区分格子。决策完全由约束求解器做出，Laya 只用于展示对比。


> `model.safetensors` / `rl_agent_config.json` / `tokenizer/` / `encoder/` 放到一个目录,
> 然后用 `--model /该目录` 完全离线运行。本项目的 `--model` 支持本地目录就是为了这个。

## 这是怎么工作的

### 扫雷的本质

每个**已揭开**的数字都是一条约束:

> 「我周围还有 N 颗雷, 分布在 M 个未揭开的格子里」

把这些约束收集起来, 就是一个约束满足问题。求解分四步:

| 步骤 | 做什么 | 复杂度 |
|---|---|---|
| 规则 1/2 | 单格推导: 约束需要 0 颗雷 → 全安全; 需要 M 颗且正好 M 个格 → 全是雷 | O(n) |
| 规则 3 | 子集推导: 若 A 的格子集是 B 的子集, 则 B\A 需要 `B.need - A.need` 颗 | O(n²) |
| 规则 4 | 对剩余约束的**连通块做完全枚举**, 得到每格的**精确**含雷概率 | O(2^cap) |
| 规则 4 | 对剩余约束的**连通块做 DFS 剪枝完全枚举**, 得到精确概率 | 剪枝后远小于 2^n |
| 规则 5 | **全局雷数约束**: 用 DP 组合各独立块, 加权出跨块一致的边际概率 | O(块数 × 雷数²) |
| 兜底 | 枚举超时或超预算的格子, 用「全局剩余雷数 / 全局剩余格数」估计 | O(n) |

规则 4 用 DFS 剪枝而非 2^n 暴力枚举：每放一颗雷就检查所有涉及该格的约束是否
仍可行，不可行立即回溯。配合节点预算与 700 ms 时间闸（deadline 传进 DFS 内部，
单个大块也无法超时）。实测地狱难度单步从 **109 秒降到 172 毫秒**。

规则 5 是原先完全缺失的：把所有互相独立的连通块看成一组，每块有若干合法方案，
各贡献不同数量的雷。用 DP 统计「总雷数 == 剩余雷数」的组合数，从而为每块加权，
得到**跨块的全局一致概率**。很多单看局部"不确定"的格子，加上这条约束后就变成必然。

> 注意：只有**全部块都精确枚举成功**时才启用规则 5。若某块走了子块拆分降级，
> 子块之间会互相重叠、独立性被破坏，DP 前提不成立 —— 强行使用会算出错误概率
> （实测在地狱难度上把安全格判成"必然是雷"）。

规则的迭代轮数就是界面上的 **推演深度**。

### Laya 在哪一步介入

只有当**约束求解无法确定**任何格子时(必须猜), 才会:

1. 把每个待判格写成一句中文:
   > 「这一格西北面是一个已揭开的 3, 它周围还有 5 个没揭开的格子, 其中还需要 3 颗雷」
2. 把这十几句话**合并成一个请求**发给 Laya(一次前向传播回答全部问题)
3. 页面把 Laya 的 P(雷) 和数学真值**并排显示**

代码**不采纳** Laya 的判断 —— 决策仍以数学为准。Laya 的输出只用于对比展示。

### 为什么合并成一个请求

Laya 的一次 `predict` 调用可以同时回答任意多个问题, 共享同一次前向传播。
扫雷一步最多 14 个待判格, 分成 14 次请求会慢 14 倍。

## 实测数据

### 推演深度有用吗 —— 2 以上完全没用

5 个固定中局 × 4 种深度, 取平均:

| 深度 | 必然安全格 | 枚举格 | 合法方案 | 耗时 |
|---|---|---|---|---|
| 1 | 0.0 | 13.0 | 5.0 | 10.6 ms |
| **2** | **13.0** | 0.0 | 0.0 | 8.9 ms |
| 3 | 13.0 | 0.0 | 0.0 | 8.3 ms |
| 4 | 13.0 | 0.0 | 0.0 | 9.4 ms |

- **深度 1 → 2 有意义**: 多找出 13 个必然安全格(需要两轮约束传播才能推导出来)
- **深度 2 → 3 → 4 数字逐位相同**: 约束在第 2 轮就收敛了, 再迭代没有新信息
- 耗时也没差别

所以界面上默认是 **2 步**。3/4 是多余的。

> 有趣的反直觉点: 深度 1 的枚举格反而更多(13 vs 0)。因为迭代少时留下的约束块更小、
> 更容易枚举; 深度 2 把约束推干净了, 反而不需要枚举。两条路殊途同归。

### 性能

单步耗时(状态栏实时显示, 求解与推理分开):

| 环节 | 耗时 |
|---|---|
| 约束求解 | 0.3 ~ 42 ms(取决于是否需要枚举) |
| **Laya 推理(14 个问题同批)** | **380 ~ 930 ms** |

瓶颈明显在推理 —— 比求解慢 **100 倍以上**。这也说明为什么"把决策交给数学"是对的。

## 界面主题

**默认深色**，右上角按钮可切换深浅色，选择记在 `localStorage`，刷新后保持。

> 没有做「跟随系统」：需求是默认深色，跟随系统会让浅色系统的用户一进来
> 就是浅色，与"默认深色"矛盾。只有你手动切过，主题才会改变。

## 后端 API

只有两个接口, 都很简单:

### `GET /api/health`

```json
{"state": "ready", "model": "english", "device": "cuda", "load_s": 13.4, "error": null}
```

`state` 取值: `pending` / `loading` / `ready` / `error`

### `POST /api/predict`

请求:

```json
{
  "state": "扫雷棋盘：30 列 16 行，一共埋了 99 颗雷……",
  "questions": {
    "c_3,1": {
      "type": "noul",
      "instructions": "第 4 行第 2 列这一格下面有地雷吗？……",
      "criteria": {"true": "这一格下面有地雷", "false": "这一格下面没有地雷"}
    }
  },
  "model": "typed-decisions"
}
```

响应:

```json
{
  "answers": {"c_3,1": {"type": "noul", "noul": 0.647, "confidence": 0.647}},
  "latency_ms": 463.2,
  "device": "cuda",
  "routing": {"model": "typed-decisions"}
}
```

和上游 [laya-playground](https://github.com/wdobry/laya-playground) 的接口形状一致,
所以这个后端可以互换使用。

## 已知限制

- **Laya 的判断不可用**(见上文实测)。项目保留它只是为了展示对比。
- **密度 >25% 基本无法通关**（实测 0/40）。这是扫雷作为 NP 完全问题的固有上限，不是代码缺陷。
- 高密度时约束求解能确定的格子急剧减少，大量局面只能猜，踩雷属正常。
- 扫雷本身是 **NP 完全**问题。约束求解器能处理的局面有限, 超出部分只能猜;
  猜测时踩雷是正常的, 不是 bug。
- 大棋盘上多数约束会连成**一个超大连通块**, 超过枚举上限。项目里做了子块拆分
  (`splitGroup`), 能算多少算多少, 拆不动的格子退化为全局估计。
- 只绑定 `127.0.0.1`, 不做鉴权, 也不适合对外提供服务。
